# Desktop hot-standby и WARM последнего основного пира

Дата: 26.09.2026. База приложения: main 6b8aa90.
Ветка: существующая codex/desktop-redundant-warm.
Статус: схема согласована 26.09.2026; план и локальная реализация разрешены
без дополнительной остановки на согласование плана. Функция ещё не реализована.

## Цель и полномочия

Пользователь разрешил полноценный hot-standby для desktop. Уточнение
«если резервирование уже реализовано — только WARM» не отменяло эту задачу.
Прежний docs-only blocker по отсутствию разрешения снят.

Область: Windows, macOS, Linux; Tic/Tak (WG) и Stray (AWG3).
Сохраняем принятые серверные контракты и работающий одиночный режим.
Без переписывания приложения, изменений modified vendor, production,
публикации, push будущей ветки и установки на пользовательские устройства.
Killswitch и запрет standalone Tic — отдельная ветка/задача, здесь не включаются.
Версию выпуска эта спецификация не назначает.

## Подтверждённые исходные условия

- commands.rs::app_start читает use_reserve_connection только на Android.
  Desktop проходит через DesktopConnectionIntent; его нельзя обходить вторым Start.
- client-core уже формирует RedundantTunnelStart и имеет API role/standby/stop.
  Наличие типов не означает готовность desktop transport/lifecycle.
- UnixTunnelController и WindowsTunnelController отправляют helper одну конфигурацию.
  В WindowsServiceBackend::start есть self.stop(): два обычных Start не дают пару.
- Unix/macOS backend хранит один API/interface, общий snapshot DNS и RouteManager.
  Windows manager использует одиночные transport service/config paths.
- Android имеет собственные Kotlin coordinator/health monitor и JNI data plane:
  два transport slot за одним TUN. Этот механизм нельзя считать переносимым на
  desktop простым использованием общих Rust-структур.
- WARM одиночной аренды уже существует. Для пары нужен Stop всей сессии и
  согласованный last-active member, а не отдельный Stop прежнего primary.

## Выбранный подход и альтернативы

Рекомендуется общий desktop session coordinator в существующем Rust runtime
с платформенными реализациями операций над двумя native-туннелями.
Не создаётся второй системный manager/service или независимый retry scheduler.
Работающий одиночный путь остаётся отдельно совместимым.

Отклонены: (1) два запуска существующего single backend без общего владельца
маршрутов/DNS; (2) замена всех desktop backend универсальным Android-подобным
userspace engine. Первый вариант некорректен, второй существенно расширяет задачу.

## Владение и границы компонентов

- DesktopConnectionIntent остаётся владельцем пользовательского желания Start/Stop
  и admission/recovery. Выбранный reserve режим фиксируется на generation Start,
  поздний ответ не должен менять уже отменённую/заменённую сессию.
- Существующий client-core/API слой отвечает за серверные операции, авторизацию,
  идемпотентность и долговечное подтверждение Stop; credentials не передаются
  произвольным native-командам и не логируются.
- Привилегированная служба владеет обоими transport slots, health observations,
  выбранным active slot, маршрутами, DNS и физическими endpoint bypass routes.
  Локальный failover должен работать без открытого UI и без roundtrip к панели.
- Общая логика решений и её тесты находятся в Rust; платформенные backend
  предоставляют start/stop slot, probe slot, select active и scoped cleanup.
  Android не переписывается: его сценарии становятся эталонами совместимости,
  а не поводом для одновременного рефакторинга Kotlin.
- IPC расширяется версионированно с проверкой capabilities. Старый helper не
  получает reserve Start, который он мог бы молча исполнить как одиночный.
  Отсутствие поддержки явно видно; обычный single Start сохраняется.

## Data plane и обязательная проверка платформ

У пары один логический владелец маршрутов/DNS. Только active member получает
пользовательский трафик; standby допускает handshake/keepalive/адресные health
пробы, которые действительно идут через него, а не через active или физическую сеть.
Оба внешних endpoint сохраняют путь через физическую сеть, включая смену gateway.
Split-tunnel, исключённые локальные сети, IPv4/IPv6 и DNS сохраняют текущую семантику.

Внутри текущих helper расширяются singleton paths/names/state до двух slots и
одного session-scoped route/DNS owner. Нельзя дважды вызвать нынешний общий cleanup.
Одинаковый серверный VIP, автоматическая маршрутизация/DNS и встроенная фильтрация
Windows WG DLL требуют проверки по backend-коду до включения двойного режима.
Предпочтение native backend не является доказательством их совместимости с парой.

Первый технический этап плана должен доказать контролируемость этих side effects
на закреплённых backend. Если для платформы невозможно независимо управлять
маршрутами или выполнить достоверную slot-пробу без замены движка, реализация
не объявляет поддержку: фиксируется конкретный блокер и пересматривается только
платформенный адаптер. Нельзя подменять hot-standby последовательным reconnect.

## Start, проверка резерва и переключение

- Primary-first: основной туннель и пользовательский трафик запускаются без
  ожидания выдачи/подготовки/handshake резерва. Ориентир Start около 5 секунд,
  без обещания точного времени до аппаратного замера.
- Standby приобретается и поднимается фоново через существующий контракт.
  Его отказ не останавливает исправный primary; статус честно показывает
  подключение без готового резерва.
- Используем принятую Android-политику подтверждения отказа, а не новый набор
  произвольных таймаутов. Primary пробы раз в 2 секунды; при подозрении запускается
  проверка standby с фазовым сдвигом около секунды, без перекрывающихся проб slot.
- Не переключаемся только по возрасту handshake и не переключаемся на резерв
  без свежего подтверждения его работоспособности. Hard failure и soft failure
  различаются; отсутствие обеих сторон передаётся существующему recovery.
- Переключение сериализовано с Stop/сменой сети. После подтверждённого локального
  переключения фиксируется local active, затем идемпотентно синхронизируется роль
  с панелью. Старые ACK/candidate ответы отсекаются session/operation/generations.
- Нет безусловного failback на прежний primary при первом успешном пакете.
  Нельзя сохранять two competing defaults или объявлять active раньше успешной
  операции data plane. Частичная ошибка имеет проверяемое recovery состояние.

## Stop, WARM и восстановление

- Stop кнопкой/quick action прекращает локальный трафик без ожидания серверной
  очистки. Сохраняется намерение Stop с точным session/operation scope; запрос
  отправляется до локального отключения и повторяется вне туннеля в фоне по
  существующей схеме, с интервалом 10 секунд до терминального подтверждения.
  Повторный HTTP attempt не создаёт новую серверную Stop operation.
- Новая Start не теряется из-за позднего Stop ACK старой сессии. Неразрешённый
  серверный ownership reconciles штатно, без выдачи конкурирующих аренд вслепую.
- При обычном Stop и согласованном warm_stop_v1 только последний фактически
  активный member удерживается за устройством на час, standby освобождается.
  После failover A→B сохраняется B. Роль сначала сверяется с серверным контрактом;
  при неоднозначном ACK нельзя угадывать retained member или заявлять успех.
- Новый Start переиспользует пригодную WARM-аренду и асинхронно получает свежий
  standby. Неподдерживаемый сервером WARM использует существующий полный Stop.
- Logout, отзыв доступа, смена runtime и непригодная аренда требуют полного
  освобождения; обычная WARM не переносится на эти операции.
- Durable минимальный session/slot/route ownership переживает crash/update.
  Перезапуск не означает безусловный повтор Start. Cleanup касается только
  проверенных ресурсов данной сессии; чужие VPN/маршруты не удаляются.
- Смена физической сети обновляет transport binding и endpoint bypass обоих
  slots, обнуляет устаревшие probe observations, но не превращает пару в single.

## Проверки и критерии готовности

1. Pure/fake-clock coordinator tests: primary-first, отложенный standby, hard/soft
   failure, мёртвый резерв, dual loss, устаревшая probe/role/candidate, Stop гонки.
2. IPC/capability tests: старые helper, некорректные scope/configurations,
   redaction/secret handling, ограничения размера запроса, idempotent retries.
3. Fake native route/process tests по каждой ОС: две независимые конфигурации,
   endpoint bypass, DNS ownership, switch rollback, start failure cleanup,
   Stop после A→B, restart ownership, network change, отсутствие чужого cleanup.
4. Core/API tests: Start→pair→role→Stop/WARM→Start, standby cleanup/reissue,
   warm_stop_v1 fallback, logout/update/revoke и crash-before-ACK.
5. Регрессии single WG/AWG3, split/DNS, существующая desktop authorization и
   Android. Host firewall/VPN в автоматических тестах не меняются.
6. До выпуска: отдельные аппаратные/packet тесты Windows/macOS/Linux с обоими
   протоколами, failover/traffic, UI close, helper crash, network change и WARM.
   Mock tests не доказывают отсутствие утечек и непрерывность TCP-соединений.

Локальную реализацию можно вести этапами, но функция не считается завершённой,
если есть только coordinator/IPC и отсутствуют native data plane или ownership.
До отдельного разрешения аппаратные проверки/установка/публикация не выполняются.

## Собственная проверка спецификации

- Устранено ошибочное ограничение задачи только WARM; desktop — все три ОС.
- Не обещано, что существующие singleton backend уже поддерживают пару.
- Разделены local failover и server role ACK; нет зависимости переключения от UI.
- Start не ждёт резерв; Stop не ждёт сетевой очистки; WARM касается last-active.
- Возможности серверов переиспользуются, но неизменность панели не объявляется
  доказанной до контрактных тестов; найденная несовместимость требует отдельного
  решения, а не скрытого production patch.
