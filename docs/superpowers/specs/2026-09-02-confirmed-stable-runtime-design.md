# Встроенная подтверждённая стабильная версия приложения

Дата: 2 сентября 2026 года

Статус: согласованная спецификация перед составлением плана реализации.

## Контекст

Nelomai активно получает новые функции. Даже прошедшее автоматические проверки
изменение может нарушить системный туннель только на конкретной комбинации ОС,
сети и устройства. Пользователь должен иметь возможность вручную вернуться к
заранее подтверждённой версии приложения и дождаться исправления, не теряя
доступ к VPN.

Текущий выпуск `0.2.15` создан из commit
`632cc4b40872c559a75e5d7104b72bae17ac91c3`. После него в `main` уже находится
крупная реализация Android hot-standby, предназначенная для `0.3.0`. Поэтому
совместимый базовый выпуск `0.2.16` должен происходить из отдельной maintenance-
линии от commit `632cc4b`, а не из текущего `main`.

## Цель

Один установщик Nelomai содержит:

- актуальный runtime `latest`;
- явно выбранный при сборке runtime `confirmed-latest-stable`;
- минимальный общий контейнер, который выбирает один runtime и сохраняет одну
  идентичность установленного приложения.

Пользователь вручную включает или выключает настройку «Использовать стабильную
версию». Переключение применяется после полного перезапуска приложения. При
установке следующего обновления выбор безусловно сбрасывается на `latest`.

## Не входит в задачу

- автоматическое переключение из-за crash-loop, ошибки запуска или отказа
  туннеля;
- аварийный системный экран или внешний shortcut для выбора stable, если UI
  выбранного runtime вообще не запускается;
- одновременная работа latest и stable;
- загрузка stable по требованию после установки;
- отдельное stable-приложение, второй package ID или второе устройство в
  панели;
- перенос настроек, lease и recovery-состояния между версиями runtime;
- изменение Android hot-standby в maintenance-линии `0.2.16`;
- поддержка iOS.

## Термины

- **Контейнер** — устанавливаемая и обновляемая системная единица Nelomai с
  одним package/application ID и собственной версией.
- **Runtime** — versioned UI, бизнес-логика и реализация туннеля, запускаемые
  контейнером.
- **Latest** — runtime текущей версии контейнера.
- **Stable** — конкретный ранее выпущенный runtime, явно указанный при сборке
  контейнера.
- **Runtime-контракт** — обратно совместимый интерфейс между контейнером и
  runtime.
- **Ожидающий слот** — выбор, сохранённый после изменения тумблера и
  применяемый при следующем полном запуске.

## Основные правила

1. В контейнере работает не более одного runtime.
2. Stable всегда задаётся точной неизменяемой версией, а не вычисляется как
   предыдущий или последний опубликованный релиз.
3. В сборку входит ранее опубликованный бинарный runtime-артефакт. Повторная
   сборка исходников старого тега вместо него запрещена.
4. Оба runtime используют один аккаунт, один `install_secret` и одну
   серверную сессию устройства.
5. Настройки, tunnel-state, lease, pending operations и recovery-записи
   runtime изолированы.
6. Изменение тумблера немедленно завершает текущий туннель, но не обязано
   автоматически перезапускать UI.
7. Новый контейнер всегда впервые запускает `latest`, даже если в предыдущем
   контейнере пользователь выбрал stable.
8. Сбой runtime сам по себе не меняет выбранный слот.

## Архитектура

### Общий контейнер

Контейнер владеет только обязанностями, которые нельзя безопасно дублировать:

- единой системной идентичностью приложения;
- версией установленного контейнера;
- проверенным манифестом latest и stable;
- выбранным и ожидающим слотом;
- общим защищённым хранилищем авторизации;
- обновлением всего установленного приложения;
- системными точками входа: Android Quick Settings, VPN permission и service
  dispatcher, desktop tray и автозапуск;
- журналом переключения и координацией полного завершения туннеля;
- проверкой целостности и совместимости runtime перед запуском.

Контейнер не реализует продуктовые функции и не принимает решений о выборе
сервера, маршруте, recovery или устройстве туннеля. Системные service/helper-
компоненты контейнера являются тонкими стабильными диспетчерами. Поведение
туннеля находится в выбранном versioned engine, чтобы новая реализация latest
не могла незаметно изменить работу stable.

### Versioned runtime

Runtime содержит:

- полный UI соответствующей версии;
- прикладную модель и API-клиент, кроме владения refresh-токеном;
- выбор соединения, lease lifecycle и recovery;
- платформенный tunnel engine и его versioned helper-код;
- собственные настройки, split-tunnel policy и диагностическое состояние.

UI runtime вызывает общий контракт для получения информации о слотах,
изменения выбора, авторизации, logout и запроса обновления. Тумблер присутствует
начиная с `runtime-v1`, но скрыт, если контейнер не предоставляет отличный от
latest stable-слот.

### Манифест контейнера

Подписанный манифест контейнера содержит как минимум:

- версию контейнера;
- версию формата манифеста;
- для каждого слота: роль, версию runtime, платформу, архитектуру, версию
  runtime-контракта, путь и криптографический хеш;
- идентификатор набора подписанных release-артефактов;
- минимальную и максимальную поддерживаемую версию контракта контейнера.

Stable не считается доступным, если он совпадает с latest, отсутствует,
повреждён или несовместим с контейнером.

## Авторизация и идентичность устройства

Текущий `StoredAuth` объединяет `install_secret`, access/refresh-токены,
сохранённые соединения, lease и незавершённые операции. В `runtime-v1` эта
структура разделяется на общий `AuthStore` и отдельное состояние runtime.

Общий `AuthStore` хранит:

- `install_secret`;
- access- и refresh-токены;
- монотонное поколение локальной сессии;
- состояние logout, необходимое для crash-safe завершения.

Runtime не читает и не записывает refresh-токен напрямую. Общий auth-broker
предоставляет операции login, получение действующего access-токена, refresh,
logout и чтение состояния авторизации. Операции сериализованы, а результат
привязан к поколению сессии. Устаревший ответ старого runtime не может
восстановить токены после logout или новой авторизации.

Если платформенному tunnel engine нужна фоновая авторизация, auth-broker
выдаёт отдельное ограниченное полномочие, привязанное к слоту, runtime-версии и
поколению общей сессии. Оно не является refresh-токеном. Переключение сначала
использует это полномочие для завершения cleanup, а затем инвалидирует его для
новых start/recovery операций исходного runtime. Новый runtime получает своё
полномочие только после применения слота.

Logout из любого runtime действует на весь контейнер: сначала завершается
активный туннель и его серверные операции, затем отзывается общая серверная
сессия и очищается `AuthStore`. Настройки слотов разрешено сохранить, но ни один
runtime после logout не может восстановить туннель без нового входа.

## Изоляция состояния runtime

Каждая версия runtime получает собственный namespace хранилища, логически
эквивалентный:

```text
runtime/latest/<runtime-version>/...
runtime/stable/<runtime-version>/...
```

В namespace находятся preferences, split-tunnel state, сохранённые
соединения, lease, pending start/stop, recovery, quick plan и runtime-
диагностика. Один runtime не десериализует состояние другого и не продолжает
его операции.

Состояние выбора слота и журнал переключения находятся вне этих namespace.
Токены и `install_secret` также не входят в runtime-state.

## Переключение runtime

### Пользовательский сценарий

В настройках показываются:

- тумблер «Использовать стабильную версию»;
- версия встроенного stable-runtime;
- активная версия runtime;
- ожидающая версия, если переключение ещё не применено.

После изменения тумблера контейнер сохраняет целевой слот и начинает
транзакцию переключения. Текущий UI продолжает работать, но туннель немедленно
завершается. После очистки показывается сообщение «Версия изменится после
полного перезапуска приложения» с действиями «Позже» и «Перезапустить сейчас».

Закрытие окна в tray не является полным перезапуском. Новый слот применяется
только после завершения UI, runtime, VPN service/helper и связанных фоновых
процессов.

Если до перезапуска пользователь возвращает тумблер к активному слоту,
ожидающий выбор отменяется. После подтверждённого завершения предыдущей
транзакции пользователь снова может запустить туннель в текущем runtime.

### Транзакция переключения

Общий журнал содержит идентификатор операции, исходный и целевой слот,
контейнерную версию и фазу:

```text
requested -> runtime_stopping -> local_stopped -> cleanup_pending -> complete
```

Порядок действий:

1. Атомарно сохранить ожидающий слот и фазу `requested`.
2. Запретить новые start/recovery операции исходного runtime.
3. Штатно остановить туннель, освободить lease и очистить автоматическое
   восстановление исходного runtime.
4. Остановить системный VPN service/helper.
5. После ограниченного таймаута принудительно завершить оставшийся локальный
   VPN-процесс.
6. Сохранить незавершённую серверную очистку как идемпотентный
   `cleanup_pending`, не возвращая старый туннель.
7. Завершить транзакцию и разрешить применение целевого слота при следующем
   полном запуске.

Аварийное завершение на любой фазе не теряет журнал. При следующем запуске
контейнер завершает локальную очистку и возобновляет идемпотентную серверную
очистку до разрешения нового tunnel start. Серверное истечение lease остаётся
последней страховкой, но не заменяет явный cleanup.

## Запуск и сброс выбора после обновления

Состояние выбора хранится как пара `container_version + selected_slot`.

При запуске контейнер:

1. проверяет подпись манифеста, хеш и контракт целевого runtime;
2. сравнивает сохранённую и установленную версии контейнера;
3. при несовпадении атомарно выбирает `latest` и удаляет ожидающий выбор;
4. завершает незакрытую транзакцию предыдущего контейнера;
5. запускает выбранный runtime.

Если stable не проходит проверку целостности или контракта, контейнер атомарно
сбрасывает выбор на latest, запускает latest и показывает причину. Это защита
повреждённой установки, а не автоматический fallback из-за ошибки runtime.

Updater всегда сообщает панели версию контейнера. Активная версия runtime не
участвует в сравнении доступных обновлений, иначе stable будет постоянно
считать текущий контейнер новым обновлением.

## Платформенная реализация

### Android

Используются один APK, один application ID, один `versionCode` и одно системное
VPN-разрешение. APK содержит общий Activity/service dispatcher и два
изолированных runtime-пакета. Versioned код, ресурсы, native-библиотеки и
tunnel engines получают непересекающиеся namespace/entrypoint. Общий
`VpnService` делегирует выбранному engine основную tunnel-логику и не содержит
изменяемую продуктовую реализацию.

Quick Settings tile управляет только выбранным runtime. Во время ожидающего
переключения запуск через плитку блокируется до полного перезапуска, чтобы
старый engine не создал новый lease.

Stable публикуется как внутренний Android runtime-артефакт, пригодный для
включения в будущий APK. Вложенный подписанный APK не используется.

### macOS

Контейнер запускает выбранный versioned runtime и tunnel helper. Все вложенные
исполняемые файлы подписываются до финальной подписи и notarization приложения.
Общий launcher проверяет манифест до запуска дочернего процесса.

### Windows

Одна установленная служба выступает стабильным dispatcher и запускает
versioned tunnel engine выбранного runtime. Два runtime не регистрируют
конкурирующие службы и не владеют общей service-конфигурацией напрямую.

### Linux

Оба runtime и dispatcher входят в AppImage. Формат, ABI, запуск, IPC и
тестовый tunnel adapter обязательны в CI. Реальный системный tunnel E2E не
считается проверенным до появления физической Linux-машины у разработчика или
тестеров.

## Сборка и выпуск

### Базовый выпуск 0.2.16

`0.2.16` создаётся из maintenance-линии от `632cc4b` и функционально сохраняет
туннель `0.2.15`. В него входят только изменения, необходимые для:

- контейнера и `runtime-v1`;
- разделения авторизации и runtime-state;
- versioned system dispatcher/engine boundary;
- crash-safe переключения;
- выпуска встраиваемых runtime-артефактов;
- тестов и диагностики новой границы.

Контейнер `0.2.16` содержит один фактически доступный runtime `0.2.16`, поэтому
тумблер скрыт. Выпуск создаёт обычные установщики и отдельные неизменяемые
runtime-артефакты для каждой поддерживаемой пары платформа/архитектура.

После проверки инфраструктурные изменения `0.2.16` переносятся в текущий
`main`. Изменения Android hot-standby не попадают обратно в maintenance-линию.

### Последующие выпуски

Release workflow получает обязательный параметр `stable_version`, например
`0.2.16`. Для каждой платформы и архитектуры workflow:

1. находит опубликованный runtime-артефакт точной версии;
2. проверяет release identity, подпись, хеш, платформу, архитектуру и
   runtime-контракт;
3. проверяет, что версия API/контрактов stable входит в явно поддерживаемый
   панелью диапазон для embedded runtime;
4. включает артефакт без повторной сборки его исходников;
5. формирует и подписывает манифест нового контейнера.

Отсутствие или несовместимость любого обязательного stable-артефакта
останавливает весь release. Workflow не имеет права тихо использовать другую
версию или собирать latest без stable.

Первый контейнер с разными слотами — `0.3.0`: `latest = 0.3.0`,
`stable = 0.2.16`.

## Размер и распространение

Оба runtime входят в установщик, поэтому переключение не требует сети. Рост
размера пакета принимается как осознанная стоимость аварийной доступности.
Сборочный отчёт должен показывать размеры latest, stable и общего контейнера,
чтобы случайное дублирование общих toolchain-артефактов было заметно.

## Ошибки и безопасные отказы

- Повреждённый или несовместимый stable не запускается; выбирается latest и
  показывается явная ошибка.
- Недоступный auth-broker не создаёт новый `install_secret`, не выполняет
  повторный login и не отдаёт устаревшие токены.
- Ошибка штатного stop переходит к ограниченному принудительному локальному
  завершению и сохраняет серверный cleanup для повтора.
- Pending cleanup не разрешает новому runtime начать туннель, пока безопасная
  сверка не подтвердит отсутствие конфликтующей операции или пока cleanup не
  будет завершён.
- Runtime crash не меняет слот и не включает автоматический fallback.
- Ошибка обновления не меняет текущий контейнер или выбор слота.
- Невозможность доказать совместимость stable останавливает сборку release.

## Диагностика

Каждый отчёт включает без секретов:

- версию контейнера;
- активный и ожидающий слот;
- версии latest и stable runtime;
- версию runtime-контракта;
- идентификатор и фазу переключения;
- результат проверки манифеста и хеша;
- источник системного действия: UI, tile, tray, autostart или updater;
- выбранный engine для системного tunnel dispatcher.

Логи не содержат токены, `install_secret`, tunnel configuration, ключи или
production-конфигурацию.

## Совместимость панели

Панель продолжает видеть одно устройство, определяемое общим
`install_secret`. Запросы приложения передают отдельно версию контейнера и
активную версию runtime там, где это нужно для диагностики и capability gate.
Версия контейнера остаётся единственным источником истины для updater и
minimum-supported policy. Поэтому standalone `0.2.16` может позднее стать
неподдерживаемым, не блокируя embedded runtime `0.2.16` внутри поддерживаемого
контейнера `0.3.0`.

Совместимость embedded runtime с серверным API учитывается отдельным
версионированным диапазоном контрактов. Выбранный stable-runtime должен
оставаться в этом диапазоне, пока он входит хотя бы в один поддерживаемый
контейнер. Release нельзя создать с runtime, чьи API-контракты панель уже не
обслуживает.

## Проверки

### Unit и contract tests

- сериализация и миграция разделённого `AuthStore`;
- сериализация поколений сессии и защита от позднего refresh после logout;
- привязка фоновых полномочий к слоту, runtime и поколению сессии;
- namespace и запрет чтения состояния другого runtime;
- state machine переключения и восстановление каждой журналируемой фазы;
- сброс выбора при изменении версии контейнера;
- проверка манифеста, хеша, архитектуры и диапазона контракта;
- маршрутизация tile, tray, autostart и updater в выбранный runtime;
- запрет tunnel start во время переключения и pending cleanup.

### Интеграционные сценарии

- обновление `0.2.15 -> 0.2.16` без потери аккаунта;
- обновление `0.2.16 -> 0.3.0` с начальным выбором latest;
- `latest -> stable -> latest` с активным и остановленным туннелем;
- отмена ожидающего выбора до перезапуска;
- аварийное завершение на каждой фазе переключения;
- timeout штатного stop и принудительное завершение VPN-процесса;
- retry идемпотентного server cleanup;
- login, refresh и logout из каждого runtime без дублирования устройства;
- update check и установка обновления при активном stable;
- повреждённый stable и несовместимый runtime-контракт;
- запуск из UI, Android tile, desktop tray и autostart.

### Платформенный E2E

- Android, macOS и Windows: установка, update, оба runtime и реальный туннель;
- Android: VPN permission, foreground service, tile и завершение UI-процесса;
- macOS: подпись, notarization, вложенные executables и helper lifecycle;
- Windows: installer upgrade, единственная служба и dispatcher lifecycle;
- Linux: AppImage, подпись/хеш, оба runtime, IPC и тестовый tunnel adapter.

Физический Linux tunnel E2E остаётся непроверенным ограничением до появления
подходящей машины и явно указывается в release checklist.

## Критерии готовности

Функция готова, когда:

- все четыре платформы собирают один контейнер с двумя проверенными runtime;
- пользователь может вручную выбрать stable и вернуться на latest;
- переключение не оставляет работающий системный VPN-процесс и не создаёт
  второй профиль устройства;
- общий login/refresh/logout корректен после многократных переключений;
- обновление контейнера сбрасывает выбор на latest;
- latest и stable сохраняют независимые настройки и tunnel-state;
- release невозможно создать без точного полного набора stable-артефактов;
- обязательная автоматическая и доступная физическая E2E-матрица проходит;
- отсутствие Linux physical E2E явно зафиксировано, а не выдано за пройденную
  проверку.
