## Объединение и ручное ревью

Сохранены common owner/auth/runtime-v1 из maintenance и Android recovery-v2,
hot-standby, reserve UI и fencing из main. Восемь конфликтных файлов разрешены
по отдельным участкам, без wholesale ours/theirs.

Выявленные и исправленные стыки:

1. Recovery-v2 API/compensation используют `AccessSnapshot` common owner,
   операционное состояние — `RuntimeStateStore`, не старое auth-хранилище.
2. Новые команды standby cleanup и task-removal liveness направляются в common
   VPN dispatcher. Cleanup не требует разрешения на новый старт.
3. Redundant-cancel tombstone перенесён в существующий runtime namespace.
   Legacy-копия сохраняется до общего ACK; повтор подготовки не затирает
   уже продвинувшуюся запись назначения. Нового формата журнала нет.
4. Сохранены reserve-state и authoritative Android projection; desktop local
   stop/cleanup UI и фоновые обновления не заменены старой реализацией main.
5. Новые тесты проверяют сохранение Rust recovery-v2 полей при legacy import,
   сериализации и protected-store roundtrip, а также запрет чтения через
   namespace stable/0.2.20.
6. Android Rust-сборка выявила отсутствующий application-метод
   `start_recovery_v2` у существующего UI-вызова. Добавлен проход через общие
   preflight/probes/lifecycle-проверки, с передачей исходного cancellation epoch
   в core и общей сериализацией intent. Проверена отмена во время preflight
   и до входа в core после probes.

Планирование, выяснение причин и ревью выполнял основной агент. Два Sol
использовались только для ограниченных кодовых изменений и их регрессий.

## NLM-027: исправлена подтверждённая часть

Legacy Quick Tile при выключенной capability штатно не имеет intent template.
Dataplane stall теперь не передаёт такой сеанс координатору measured intent.
После исчерпания существующего rebind допускается **один локальный перезапуск
того же native-туннеля с той же арендой и конфигурацией**. Проверяются текущее
владение, intent generation, пользовательское desiredActive, отсутствие logout,
redundant cleanup и runtime start admission. Проверки отмены выполняются до
остановки, перед стартом и после него. Частично запущенный туннель закрывается.

Новый lease не запрашивается; нет нового recovery coordinator, persisted state,
API или изменений keepalive/таймаутов. Native UP не считается доказательством
доступности сети. При неудаче/повторном исчерпании работает прежняя остановка,
без перехвата уже начатого пользовательского stop.

Причина исходной потери входящего UDP **не установлена**. Нужна отдельная
проверка S23u по USB ADB: Quick Tile с capability=false, Wi-Fi/cellular,
восстановление реального трафика и остановка во время recovery.

## Повторное ревью hot-standby и исправления

После интеграции отдельно проверен исходный hot-standby из main. Конфликтов
Git не осталось, но выявлены четыре унаследованных дефекта управляющей логики:
зависание при отказе активного слота во время подготовки кандидата, пропуск
health-контроля после отключения резерва, отсутствие автоматического восполнения
резерва и повторение уже подтверждённого release на каждом tick.

Исправления ограничены существующими coordinator/health monitor/recovery store:

- Готовый кандидат сначала проходит штатный commit, затем переключается по
  новой canonical identity. Если commit невозможен или кандидат ещё не готов,
  отказ активного слота запускает существующий total-loss recovery; неподтверждённый
  lease не активируется.
- Health-контроль активного слота сохраняется после отключения резерва.
  Выключенный резерв исключён из целей переключения даже при неудачном local stop.
- Рабочий tick назначает замену отсутствующего или подтверждённо отказавшего
  резерва. Существующая задержка 60 секунд и отмена замены при восстановлении
  сохранены; таймауты и keepalive не менялись.
- Один дополнительный флаг `standbyReleasePending` в существующем recovery retry
  отличает незавершённый release от ACK, в том числе после смерти процесса.
  Старые disabled-записи без флага безопасно повторяют release один раз.
  Ошибка чтения метрик не блокирует cleanup retry.

Добавлены 18 сценариев через реальные coordinator/store и 2 проверки совместимости
recovery-записей. На исходном коде подтверждено падение регрессий; после правок
Android: 724 tunnel-plugin + 10 runtime-common + 24 app = **758 passed**, без
failures/errors/skips. Host Go `go test -race -count=1 .` также прошёл.
Повторное саморевью новых изменений: блокирующих замечаний не найдено.
Сохраняются предупреждения Gradle о deprecated features; аппаратных проверок нет.
Изменения локальные в `codex/integrate-0.3.0`, без push/deploy/release.

### Дополнение: совместимость с панелью и Retry-After

Следующее ревью воспроизвело два пропуска прежних unit-тестов: серверный commit
отклонял кандидата в пустом слоте, а acquire игнорировал `Retry-After`.

- Панель: отдельный worktree `nelomai-panel/.worktrees/hot-standby-empty-slot`,
  ветка `codex/hot-standby-empty-slot`, база `d64e018`. Commit разрешён при
  отсутствии current-member только если canonical slot также пуст. Проверки
  поколений и запрет замены активного lease сохранены; миграций БД нет.
- Android: первоначальный acquire и replay подготовки кандидата сохраняют срок
  повтора в существующем `nextRetryAtUnix`, используя имеющийся parser/fallback
  `ConnectionIntentErrorPolicy`. Operation ID сохраняется; health-контроль не
  приостанавливается. Новых форматов состояния и таймаутов не введено.
- Проверены реальные серверные `acquire → commit` для пустых A/B, запрет
  перезаписи занятого canonical slot без current-member, восстановление срока
  повтора после рестарта и реакция на отказ активного туннеля во время ожидания.
- Итог: **193 серверных теста и 762 Android-теста прошли**. Production-файл панели
  проходит Ruff; в существующих тестах остаются 4 прежних B023 (проверены на HEAD).
  `git diff --check` проходит в обоих worktree. Ревью выполнено основным агентом.

Обе правки остаются локальными и незакоммиченными. Перед использованием нового
восполнения резерва в 0.3.0 требуется отдельно развернуть совместимую панель.
Это не разрешение на deploy: production и stable 0.2.20 не изменялись.

### Дополнение: истечение кандидата после потери acquire-ответа

Исправлен подтверждённый на ревью сценарий: ответ acquire потерян, за время
backoff кандидат истёк по серверному TTL, повтор прежнего operation ID возвращает
`operation_id_conflict`. Теперь Android сверяет canonical membership через
существующее подтверждение активной роли (`reportRole`), а не через полный
recovery с повторной выдачей конфигураций. Сверка не зависит от доступности
старого резервного агента. После подтверждения текущей сессии и активного lease
устаревший локальный кандидат останавливается, использованный ID снимается;
обычный health tick при необходимости назначает новую операцию с прежней
60-секундной задержкой. Активный native-туннель не перезапускается.

При ошибке сверки или остановки кандидата сохраняются его durable identity,
operation ID и backoff. Отмена подключения не перезаписывается. Временные ошибки
по-прежнему повторяют тот же ID с `Retry-After`; TTL, fallback и формат checkpoint
не менялись. Новых endpoint, миграций и изменений production-кода панели для
этой правки нет.

Добавлены 7 Android-регрессий и серверный тест полного пути
`acquire → TTL cleanup → отказ старого ID → role acknowledgement → новый acquire → commit`.
Основные регрессии проверены RED → GREEN; дополнительный RED подтвердил зависимость
первого варианта от недоступного полного recovery, затем использован role endpoint.
Итоговый прогон: **769 Android-тестов, 194 теста панели — успешно**.
Личное ревью выполнено без субагентов. Сохраняются прежние Gradle deprecation
warnings и 4 baseline Ruff B023 в серверных тестах. Аппаратных проверок,
commit/push/deploy/release не было; stable остаётся 0.2.20.

### Дополнение: потеря успешного commit-ответа

Исправлен соседний дефект, существовавший до предыдущей правки: после принятого
панелью commit и потери ответа клиент повторял запрос со старым поколением.
Реальный ответ — `session_membership_conflict`, а не `operation_id_conflict`;
соответствующий Android-тест исправлен и серверный контракт закреплён тестом.

- Commit с неопределённым результатом и replay acquire с конфликтом поколений
  используют ту же сверку через подтверждение роли. Если именно ожидаемый кандидат
  уже является current-member в ожидаемом слоте, выполняется обычное локальное
  завершение commit. Активный туннель и конфигурации не перезапускаются.
- При недоступной сверке сохраняются кандидат и operation ID; существующий
  `nextRetryAtUnix` теперь ограничивает и повторы commit. При временной ошибке
  отсутствие кандидата в canonical current-members не считается его истечением.
- Если commit явно отклонён по membership при неизменных поколениях и прежнем
  активном участнике, кандидат уже не может быть принят с этим состоянием
  (в частности, после TTL cleanup). Применяется прежняя локальная очистка и
  штатное планирование новой операции; неуспешная очистка сохраняет checkpoint.
- Обычный и восстановленный commit используют общий путь с exact-checkpoint
  записью, чтобы ответ не перезаписал конкурентную отмену подключения.

Добавлены 6 Android-регрессий, исправлен существующий тест принятого кандидата,
добавлен серверный тест потерянного commit-ответа и расширен TTL-тест.
Подтверждён RED → GREEN. Финальный прогон: **775 Android-тестов и 195 серверных
тестов прошли**, `git diff --check` чистый. Личное ревью выполнено без субагентов;
прежние Gradle warnings и 4 Ruff B023 не относятся к новым изменениям.
Изменения локальные, без аппаратных проверок, commit/push/deploy/release.
Stable 0.2.20 и production не менялись.

### Дополнение: срочная сверка кандидата во время backoff

Устранён найденный на ревью побочный эффект commit backoff: при отказе активного
туннеля ожидание фонового повтора больше не блокирует сверку уже принятого панелью
готового кандидата. Только failover-вызов получает `forFailover=true`; внутри
действующей задержки выполняется одна сверка через существующий role endpoint.
При подтверждении вызывается обычное локальное завершение commit и переключение.
Acquire/commit раньше срока не повторяются, native-слоты не перезапускаются.

Если панель недоступна или кандидат ещё не принят, сохраняется прежний путь
total-loss recovery, без слепой активации и повторных срочных запросов на каждом
тике. Конкурентная отмена подключения не перезаписывается. Фоновый backoff,
таймауты, API и формат checkpoint не менялись.

Четыре новых регрессии проверены RED → GREEN: успешный failover до retry deadline,
одна неуспешная срочная попытка, отказ активации непринятого кандидата и отмена
во время сверки. Личное ревью выполнено без субагентов. Общий Android `gradlew test`
для всех вариантов прошёл; основной debug-набор — **779 тестов**, серверный
`tests.test_client_connections` — **195 тестов**, без failures/errors/skips.
Сохраняются предупреждения Gradle/Kotlin; `git diff --check` проходит.
Изменения локальные, без commit/push/deploy/release и аппаратных проверок.
Production и stable 0.2.20 не изменялись.
